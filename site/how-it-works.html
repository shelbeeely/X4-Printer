How it works

X4 Print Inbox turns an Xteink X4 e-paper device into a wireless print inbox and offline approval terminal. A Raspberry Pi Zero W acts as a normal network printer that any OS's built-in print dialog can find, no drivers required. The X4 downloads new documents on wake, lets you read and approve or reject them fully offline, and syncs the approval back later — directly on the home LAN, or through a lightweight cloud relay when you're away from home.

Three components

Pi print server — receives print jobs over IPP (so it shows up in any OS's print dialog, no drivers), keeps the original document untouched, converts it to the X4's native page format, and exposes a small sync API the X4 talks to on the LAN. It also forwards approved jobs to the physical network printer via CUPS and polls the relay for approvals that arrive while you're away from home.

X4 firmware — runs on the device itself: syncs pending documents down over Wi-Fi, provides the offline reading and approve/reject UI, records your decisions locally, and manages the device's deep-sleep schedule so it spends almost all of its time completely powered down.

Cloud relay — a small, optional store-and-forward service. It carries only approval envelopes (device ID, job ID, action, timestamps) — never document bytes — so the X4 can approve or reject a print while away from home without exposing the home network.

Wake, sync, sleep

The X4 is asleep almost all the time. Each time it wakes — from a button press or a scheduled timer — it runs a short, bounded sync sequence and goes straight back to sleep:

  1. Wake up, from a button press or an RTC timer.
  2. Connect to the strongest saved Wi-Fi network, with a bounded timeout. If no network is reachable, that's treated as normal — the device skips straight to shutting down, not an error state.
  3. Ask the Pi which documents are pending.
  4. Stream each new document down to the SD card in small chunks, computing a SHA-256 checksum as it goes — the full document is never held in memory at once.
  5. Verify the checksum against the one the Pi sent. A match acknowledges the download and marks the job ready to read; a mismatch discards the partial file and leaves the job pending for the next wake.
  6. Send any approve/keep/delete decisions made since the last wake back to the Pi directly, or to the relay if the Pi isn't reachable on the current network.
  7. If that sync drained new approvals, repeat the fetch-and-drain once more (capped at two passes total, so a slow or misbehaving server can never keep the radio on indefinitely).
  8. Turn the Wi-Fi radio off.
  9. Power down and go back to deep sleep.

While you're actively reading or approving documents in the on-device UI, the sync sequence above only runs once, at wake. Further approvals you make during that session are queued locally and sent on the next wake, so the radio stays off for the rest of your interactive session. Nothing in this design requires the X4 to be reachable or wakeable remotely — it never listens for an inbound connection.

Why this is reliable

Approvals can't double-apply. Every approval the X4 sends carries a unique ID it generated itself. The Pi treats that ID as the single source of truth for "has this approval already happened?" and applies the approval (e.g. sending a job to the printer) and records it as applied in one atomic step. So if the same approval arrives twice — a retry after a dropped connection, or the same approval showing up via both the direct LAN path and the relay — the Pi recognizes the duplicate and returns the original result instead of printing the document again.

The firmware never runs out of memory. The X4's microcontroller has a small, fixed amount of working memory shared between Wi-Fi, the display, and the app itself. The firmware never holds a whole document in memory — downloads and page rendering both stream through small fixed-size buffers a few kilobytes at a time, regardless of how large the document is. The list of pending jobs and queued approvals is similarly capped at a fixed size; once full, the device asks you to archive or delete something rather than silently growing without bound.

The network exposure is deliberately narrow. The Pi's sync API is TLS-protected and requires a per-device token, and it's never exposed beyond the home LAN — no port forwarding, no inbound rule on the home router. The relay is also TLS-protected and sees only IDs, actions, and timestamps by default, never document contents, and it can't cause a print by itself: the Pi independently re-checks the device token before ever acting on an approval it received through the relay.
