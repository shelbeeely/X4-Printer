# Setting Up the Xteink X4

## 1. Build and flash

```sh
cd firmware
git clone https://github.com/Free-Ink/freeink-sdk   # vendor the SDK checkout the platformio.ini symlinks expect
pio run -e xteink_x4
pio run -e xteink_x4 -t upload
```

`platformio.ini` mirrors `freeink-sdk/platformio.sample.ini`'s `[env:xteink_x4]`
(tightest single-device C3 build — see `docs/architecture.md`). If you keep
the SDK checkout somewhere other than `firmware/freeink-sdk`, edit the
`symlink://` paths in `platformio.ini`'s `[base].lib_deps`.

Host-side unit tests (pure-logic modules, no Arduino toolchain or hardware
needed) live separately:

```sh
cd firmware/test
cmake -B build && cmake --build build
ctest --test-dir build --output-on-failure
```

## 2. Provision the SD card

Format a microSD card FAT32, and create these files/directories at its
root (all written by tools on the Pi, then copied over — see
`docs/setup-pi.md` step 5):

```
/system/device.json      <- from pi-server/tools/pair_device.py
/system/pi_ca.pem        <- pi-server's tls/server.crt (pinned CA for the sync API)
/system/wifi.json        <- see below
/system/relay_ca.pem     <- optional, only if you're pinning the relay's cert (docs/relay.md)
/inbox/                  <- created automatically; downloaded XTC files + index.json
```

`wifi.json` isn't generated by any tool yet in this prototype — write it by
hand (or add credentials from the on-device UI once that's wired up to save
via `config::WifiStore`, an extension point the store already supports):

```json
{
  "last_connected_ssid": "",
  "networks": [
    {"ssid": "YourHomeWiFi", "password": "yourpassword"}
  ]
}
```

Firmware re-encodes the password (XOR-obfuscated against the device MAC,
base64) the first time it saves the store, so after first boot you can
overwrite this plaintext version on the card if you'd rather not leave it
readable — see `firmware/src/config/WifiStore.h` for exactly what
protection that obfuscation does and doesn't provide.

Insert the card into the X4.

## 3. First boot

Power on (or press the power button). The firmware:

1. Determines why it woke (cold boot counts as a button-class wake — see
   `firmware/src/power/SleepManager.cpp`).
2. Connects to the strongest saved Wi-Fi network it can see.
3. Runs one sync pass (downloads any pending jobs, drains an empty approval
   outbox — nothing to do yet on a fresh device).
4. Opens the Print Inbox UI.

If `/system/device.json` is missing or Wi-Fi isn't configured, the sync
pass is a no-op (`SyncManager::runFullSync()` returns immediately, see
`docs/architecture.md`) and the Inbox screen shows "Inbox empty" — that's
expected until you've paired the device and printed something.

## 4. Using the Print Inbox

- **Inbox screen**: lists downloaded documents (`[*]` unread, `[P]`
  print-queued, `[K]` kept, `[D]` marked for delete). D-pad up/down to
  navigate, Confirm to open.
- **Reader screen**: pages through the selected document (Left/Right or
  Up/Down to turn pages). The center footer button opens the action menu;
  Back returns to the Inbox.
- **Action menu**: Print / Keep / Delete / Cancel. Choosing one durably
  enqueues an approval (`firmware/src/store/ApprovalOutbox.*`) *before* any
  network attempt — this is the "approval is saved locally" step from the
  task's critical workflow, and it survives a reboot or dead battery
  between now and the next sync.
- **Sync Now** (Inbox footer): triggers an immediate sync pass without
  waiting for the idle-sleep timer. Useful right after you know you've sent
  a print job and want it to show up now.

The device sleeps automatically after ~90 seconds of no button presses
(`kIdleSleepTimeoutMs` in `firmware/src/main.cpp`), and separately wakes on
its own every hour to sync silently and go straight back to sleep without
ever lighting the screen — see `docs/architecture.md`'s wake sequence.
Both intervals are compile-time constants; adjust and reflash if you want a
different cadence.

## 5. Using the Web UI

The Inbox screen's footer has a **Web UI** button for checking/managing
the queue from a phone browser without touching the physical buttons —
see `docs/architecture.md` "On-device Web UI" for the design, and
`docs/security.md`'s section of the same name for the full tradeoff
writeup (short version: it's off unless you turn it on, PIN-gated, plain
HTTP, and shuts itself off on the same idle timer as everything else).

1. Press **Web UI** on the Inbox screen, then choose:
   - **Use Wi-Fi** — joins a network from your saved credentials, same as
     a normal sync. Fails with "No known Wi-Fi network in range" if none
     is visible; use Hotspot instead.
   - **Use Hotspot** — broadcasts the device's own network (SSID/password
     shown on screen, freshly generated each time) so a phone can connect
     directly with no router involved. If a saved network also happens to
     be in range, the device joins it in the background and bridges the
     hotspot to it, so your phone keeps its own internet access instead of
     losing it for the session — the status line shows `(+Internet)` when
     this kicked in. See `docs/architecture.md` "Hotspot internet
     passthrough" and `docs/security.md`'s section of the same name.
2. The screen then shows a URL and a 6-digit PIN. On your phone: connect
   to the shown network (skip this for Wi-Fi mode if you're already on
   it), open the URL in a browser, and enter the PIN once.
3. From there: view the queue, and tap Print/Keep/Delete on any job — it
   queues the same durable approval the physical action menu would,
   synced to the Pi on the device's next wake (or immediately if you also
   hit Sync Now on the device itself). **Preview** decodes the job's
   on-device XTC page right there in the browser (works in either mode,
   including Hotspot with no network beyond the phone). In **Wi-Fi mode
   only**, if your `device.json` includes a `pi_admin_base_url` field
   (written automatically by `pair_device.py` when the Pi's admin console
   has a password set — see `docs/architecture.md` "On-device Web UI
   full-document preview"), a **View full document** link also appears,
   opening the original file straight from the Pi in a new tab (the Pi
   admin password logs you in there, once, via your browser's own
   prompt).
4. **Stop** (footer button on the Web UI screen) ends the session
   immediately; otherwise it ends on its own after ~90 seconds of no
   activity from the phone, same idle timer as the rest of the UI.

## 6. Remote approval away from home

Once `docs/relay.md` is set up and `device.json` includes the relay fields
(re-run `pair_device.py`, or hand-edit the JSON to add
`relay_base_url`/`relay_account_id`/`relay_account_token`), the device
automatically falls back to the relay for approval delivery whenever the
Pi's direct sync API isn't reachable on the current network — no separate
"remote mode" toggle to remember. See `firmware/src/sync/SyncManager.cpp`'s
`drainApprovalOutbox()`.

## 7. Troubleshooting

- **Inbox stays empty after printing**: confirm the Pi's CUPS queue is
  configured and the print actually completed on the sending computer's
  side (IPP accepts and stores the job immediately; it doesn't wait for
  approval). Then wake the X4 and use Sync Now.
- **"Could not open this document from SD"** in the reader: the XTC file
  didn't finish downloading/verifying — it should auto-retry on the next
  sync (`SyncClient::downloadJobToSd` deletes a hash-mismatched partial
  file rather than leaving a corrupt one, see `docs/architecture.md` wake
  step 5).
- **Approvals never leave the device**: check that both `/system/pi_ca.pem`
  matches the Pi's *current* certificate (regenerate + re-copy if the Pi's
  hostname/IP changed, see `pi-server/tools/gen_selfsigned_cert.py`) and
  that the Pi's `xteink-print-server` service is running
  (`systemctl status xteink-print-server`).
- **Web UI won't load / wrong PIN**: the PIN and hotspot password are
  regenerated every time you press Web UI — use the one currently shown
  on the device screen, not one from an earlier session.
